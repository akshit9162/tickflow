End-to-end latency is mostly queueing: with 64 orders in flight, p50 is about 64 ÷ throughput (Little’s law). The engine’s worst call in a million, 153 ms, was a GC pause. “Power loss” follows from the fsync design; the crash test kills the process, not the power.

One thread owns the book

No locks in matching, and the log order is exactly the execution order.

  1. Queue

    Requests arrive over a bounded channel; callers wait when it is full.

  2. Append to the log

    Each record is [length][CRC32][payload].

  3. Match

    Price-time priority, integer ticks, O(1) cancel lookup.

  4. Fsync once per batch

    Up to 256 queued orders share one fsync of about 3 ms. Under light load a batch is one order.

  5. Acknowledge the batch

    Trades go to the WebSocket feed and SQLite.

Replay

On start the log is replayed; a torn last record fails its checksum and is cut.

Idempotent retries

The same clientOrderId returns the original result, even after a restart.

SQL bars

Minute OHLC and VWAP with window functions over 1M trades. Last hour: 16.3 ms with the index, 82.2 ms without. A full day: 1.1×.
